# 4D 施工模拟助手

## 一句话定位

把「某项目的 4D 施工模拟」拆成可执行的任务分解、关联方法、软件操作、导出设置与检查清单，**重点不是做出一段好看的动画，而是查出施工组织中的时空冲突**。

## 何时触发

- 「我要做 XX 项目的 4D 施工模拟」
- 「XX 项目怎么做 4D」「4D 模拟怎么规划」
- 「Navisworks TimeLiner 怎么用」「进度计划怎么挂到模型上」
- 「4D 模拟怎么做不准 / 为什么做出来是假的」
- 「4D 动画怎么导出」「导出后客户打不开」
- 「出一份 4D 模拟检查清单」

## 工作流程

```
识别项目类型（别名自动归一）
        ↓
读知识库 → 施工段划分依据 + WBS + 关联策略 + 播放视角 + 专属风险
        ↓
读规范库 → TimeLiner 8 阶段 37 步 + 导出参数 + 日历核对 + 风险雷达 + 检查清单
        ↓
生成成果：
  ① <项目名>_4D模拟方案.html  —— 10 章节 / 12 张表，自带色标，可打印
  ② <项目名>_4D模拟方案.md    —— 同内容 Markdown，便于二次编辑
  ③ <项目名>_4D模拟检查清单.md —— 8 节 62 项可勾选，可直接打印
```

## 执行命令

```bash
PY="C:/Users/52248/.workbuddy/binaries/python/envs/default/Scripts/python.exe"
S="C:/Users/52248/.workbuddy/skills/bim-4d-simulation/scripts/sim_builder.py"

# 0) 查看知识库覆盖情况
"$PY" "$S" --list

# 1) 主路径：按项目类型生成（推荐）
"$PY" "$S" --project 盾构隧道 --name "XX地铁区间" --goal L3 \
        --source "Primavera P6" -o 输出目录 --checklist-only

# 2) 自定义数据渲染成品（用户已有 WBS / 风险清单时）
"$PY" "$S" --input data.json --name "XX项目" -o 输出目录

# 3) 空白模板（通用骨架 + 空白检查清单）
"$PY" "$S" --template --name "4D模拟检查清单" -o 输出目录

# 4) 只要 JSON 摘要（用于自检或程序调用）
"$PY" "$S" --project 教学楼 --name "XX中学教学楼" --json-only
```

### 参数

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| `--project` | 项目类型或别名 | 铀矿巷道 / 地下综合管廊 / 教学楼 / 盾构隧道 / 基坑支护 / 双拼别墅 / 英雄纪念碑 |
| `--goal` | `L1` / `L2` / `L3` | 模拟档位，**默认 L2**。支持「宏观」「周计划」等中文说法 |
| `--source` | 自由文本 | 进度计划来源：微软 Project / Primavera P6 / Excel CSV / Asta Powerproject |
| `--input` | JSON 路径 | 用自定义数据覆盖知识库内容 |
| `--checklist-only` | 开关 | 额外输出独立检查清单 Markdown |
| `--json-only` | 开关 | 只输出 JSON 摘要 |

### 模拟档位怎么选（重要）

| 档位 | 用途 | 粒度 | 任务量 |
| --- | --- | --- | --- |
| L1 | 投标演示、领导汇报、开工交底 | 按楼层 / 分部工程 / 标段 | 30~80 条 |
| L2 | 月度生产会、多专业穿插协调 | 按施工段 / 流水段 / 专业 | 200~600 条 |
| L3 | 周计划、机械服务范围、堆场转换 | 按流水段 × 工序 | 1000 条以上 |

★ 档位决定了后续所有拆分深度。**先让用户回答「这次模拟要帮项目团队做什么决定」，再定档位。** 目标不清会导致建模团队无限补细节、计划团队仍只给粗颗粒度横道图。

## 核心设计取舍（回答用户「为什么这样做」时必须说清）

### 1. 强制要求三类任务类型齐全

WBS 中每个项目都必须包含 **Construct（建造）/ Temporary（临时）/ Demolish（拆除）** 三种任务类型，`--list` 会输出校验结果。

理由：临时设施若全部用 Construct，画面中它们会永久存在。主体已封顶而塔吊、围挡、便道还原封不动——单看每个对象都没错，合在同一时点就失真，而且会遮挡永久工程的工作面，导致空间关系误判。**这是「4D 模拟变成动画片」最常见的成因。**

### 2. 施工段划分依据是各类项目最核心的差异

同样是「分段」，依据完全不同：

| 项目类型 | 划分依据 | 为什么 |
| --- | --- | --- |
| 铀矿巷道 | 中段 + 勘探线间距（25/50m） | 每段要对上一块确定的地质资料 |
| 地下综合管廊 | 变形缝 / 施工缝（20~30m） | 模板周转与钢筋加工的自然分界 |
| 教学楼 | 后浇带 / 变形缝 + 楼层 | 混凝土应力释放边界，即班组流水单元 |
| 盾构隧道 | 环号（1.2/1.5m），任务按环组聚合 | 以环计量；但逐环建任务会让任务表爆炸 |
| 基坑支护 | 分区开挖 + 支撑道数（工况） | 安全评价与监测数据都以工况为单位 |
| 双拼别墅 | 栋号 + 楼层 | 这类项目的核心诉求是分批交付次序 |
| 英雄纪念碑 | 竖向分段（受吊装能力约束） | 分段由起重设备决定，不由设计偏好决定 |

### 3. 诚实标注「标准要求」与「软件功能」的边界

- **GB/T 51235-2017**（第 6 章施工模拟、第 8 章进度管理）是规范要求；
- **Construct / Demolish / Temporary 三种任务类型、各种关联规则、Early/Late 外观定义**是 Navisworks 的软件功能。

★ 方案书与检查清单中均明确要求分开表述，**不要把软件操作说成规范条文**。评审时这是硬伤。

### 4. 交付物必须包含三件，不是只有视频

1. 4D 模拟动画（MP4）+ 关键节点截图集；
2. **优化后的进度计划**（根据模拟结果修正后的，不是原始计划）；
3. **时空冲突清单**（冲突位置、涉及任务、建议调整方式）。

理由：只交付一段视频，等于把 4D 当成了动画制作。第 2、3 项才是决策价值所在。

### 5. 主动指出「结果完全没有问题」是危险信号

方案书与检查清单中都写入这一条：**一个做对了的 4D 模拟必然会查出冲突。** 若播放顺畅、挑不出问题，通常说明拆分深度不够、关联不完整（存在大量漏挂），或只查了时间没查空间。这是帮用户避免「交付了一份看起来很好但没用的东西」。

## 维护与扩展

### 加一个项目类型

在 `assets/simulation_kb.json` 的 `projects` 下新增一个键，包含：

```json
{
  "category": "……",
  "aliases": ["别名1", "别名2"],
  "intro": "这个类型的 4D 模拟核心是什么",
  "segment_basis": {"primary": "…", "detail": "…", "why": "为什么这样划分"},
  "wbs": [{"code": "1.1", "task": "…", "task_type": "Construct|Temporary|Demolish",
           "dur": "…", "pred": "…", "owner": "…", "model_filter": "…", "note": "…"}],
  "linkage": {"strategy": "…", "naming": "…", "activity_id": "…"},
  "key_views": [{"name": "…", "purpose": "…", "camera": "…", "note": "…"}],
  "time_scale": "…",
  "temp_facilities": [{"item": "…", "in": "…", "use": "…", "out": "…", "note": "…"}],
  "risks": [{"risk": "…", "why": "…", "check": "…"}],
  "pitfalls": ["…"]
}
```

**约束**：`wbs` 必须包含 Construct / Temporary / Demolish 三种任务类型，否则 `--list` 会报缺项。

### 改阈值与参数

`assets/standards.json` 是唯一数据源：导出参数在 `export_settings.recommended`，检查项在 `checklist.sections`，风险雷达在 `risk_radar`。改完重跑即生效，不用动代码。

## 故障排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 报 `JSONDecodeError` | `assets/*.json` 被写坏（含未转义引号或结构断裂） | 用 `python -c "import json;json.load(open('assets/simulation_kb.json',encoding='utf-8'))"` 定位行列，按提示修 |
| 项目类型识别错 | 别名命中冲突 | 检查 `aliases`；脚本采用三级匹配（精确 → 精确别名 → 最长别名包含），**单字别名不参与子串匹配**以防误伤 |
| 输出全是通用骨架 | 项目类型不在库内 | 属预期行为（会标红提示「未收录在库」）；要支持则按上文补键 |
| 占位符没标红 | 渲染路径未走 `todo_hl` / `_highlight_html` | 新增字段时统一走 `<div class='sub'>` 包裹，由单元格函数处理 |
| 占位符出现嵌套 span | 对已高亮的字符串重复高亮 | 用 `_highlight_html`（内含 stash 机制跳过已高亮部分），不要直接再调 `todo_hl` |
| 大 JSON 写入被截断 | 单次写入内容过长（曾出现 >46KB 被截断致 JSON 损坏） | 拆成两次写入，或先写主体再用补丁脚本追加尾部，写后必须校验 JSON |
