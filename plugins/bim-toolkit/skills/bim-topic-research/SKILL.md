# BIM 选题调研助手

## 用途

把「帮我调研 XX 方向的 BIM 选题」这类需求，转成一份**案例可查证、选题可开题**的调研报告。

覆盖方向：铀矿工程 / 地下综合管廊 / 盾构隧道 / 基坑支护 / 建筑工程。其他方向走通用检索模板。

---

## 触发方式

用户说出以下任一类诉求即触发：

- 「帮我调研 XX 方向的 BIM 选题」
- 「XX 方向有什么 BIM 选题可以做」/「BIM 毕业设计选题」/「开题方向」
- 「铀矿工程/管廊/盾构/基坑/建筑 的 BIM 应用案例有哪些」
- 「给我一份选题报告模板」

---

## 执行流程

### Step 1 · 识别方向

从用户话语中提取方向，归一化后查 `assets/case_library.json`。

别名自动归一：「铀矿」→铀矿工程、「管综/管廊」→地下综合管廊、「地铁/隧道」→盾构隧道、「深基坑/围护」→基坑支护、「老旧小区/医院」→建筑工程。

**命令**：

```bash
python scripts/research_builder.py --list
```

列出库内全部方向、案例、来源 URL——**先看库，再决定要不要检索**。

### Step 2 · 检索近三年案例（核心步骤）

**库里没有的方向必须联网检索，禁止凭记忆编造案例。**

库内已有方向，也建议做一次联网复核，确认信息时效性并补全检索记录表。

严格按 `references/search-playbook.md` 执行：

1. **宽检索**（对象词 + BIM）→ 摸清案例总量与实践单位
2. **窄检索**（技术词 + 价值词）→ 补齐技术细节与数据指标
3. **反查**（已知实践单位 + 对象词）→ 挖掘同方向其他项目
4. **约束检索**（本选题特定前提）→ 确认可行性边界条件

时间窗口默认**近三年**。每条案例必须落到可访问的来源 URL。

### Step 3 · 写成案例卡片

按 `references/case-card-spec.md` 规范，每个案例填齐：`title / project / year / source / url / problem / modeling_points / data_points / fit_for_topic`。

关键要求：
- `problem` 必须有**因果链**，不能只有症状
- `modeling_points` 必须是**可执行动作**，不能是「优化管线综合」这类目标式表述
- 数字直接抄原文，不做换算放大

### Step 4 · 拟定选题

用 `references/topic-evaluation.md` 的四维尺（案例支撑 / 痛点真实 / 可行性 / 创新点）检验选题，并按「收窄法」控制范围。

选题理由四条论据缺一不可。**最危险的组合是「案例强 + 痛点真 + 可行 + 无创新」**——那只是工程实践报告，不是研究。

### Step 5 · 渲染报告

用 `--input` 传结构化 JSON 渲染正式报告（主路径）：

```bash
# 先写 research_data.json（结构见下方「输入格式」）
python scripts/research_builder.py --input research_data.json --name "项目名_方向" -o 输出目录
```

两种快捷模式：

```bash
# 草稿模式：案例从种子库带出，其余章节留骨架，适合快速看方向
python scripts/research_builder.py --direction 铀矿工程 --project "X矿" -o out/

# 空白模板：用户只要一张待填的报告模板时用
python scripts/research_builder.py --template -o out/
```

输出：`{名称}_选题报告.md` + `{名称}_选题报告.html`（HTML 可直接打印/发群，自带来源超链接）。

## 报告结构（9 个必需章节）

| 章节 | 内容 |
| --- | --- |
| 一、调研方向 | 方向 + 范围界定 + 为什么值得做 |
| 二、选题名称 | 主选题 + 3 个备选 + 命名模式参考 |
| 三、选题理由 | 案例支撑 / 痛点真实 / 可行性 / 创新点 |
| 四、AI 检索记录 | 检索式、来源、命中与采用数、筛选说明 + 证据强度分级 |
| 五、典型案例分析 | 3 个案例 ×（解决的问题 + 可借鉴建模点 + 可引用数据） |
| 六、建模设想 | 建模范围、软件路线、模型深度 LOD、关键难点、注意事项 |
| 七、预期成果 | 成果物 + **可量化指标** |
| 八、小组分工与进度计划 | 角色分工 + 分阶段里程碑 |
| 九、风险与对策 | 数据 / 技术 / 进度 / 协作 / 选题 五类风险 |

## 关键设计取舍（别丢）

1. **案例必须可回溯**。库里每个案例都带 `source` 与 `url`，渲染时无 URL 的案例会被打上红色「缺少来源 URL·交付前须补全」标记。这是刻意设的卡口——选题报告一旦引用了查不到出处的案例，整个调研的可信度就废了。

2. **占位符标红**。未填内容渲染为 `〔待补充〕` 并标红，交作业前肉眼可扫出漏填项。

3. **检索记录里做证据强度分级**。A 级（官方发布/核心期刊，可直接引用）、B 级（行业媒体，需交叉验证）、C 级（自媒体，仅作线索）。选题报告要交给老师评审，来源可信度必须先自己说清。

4. **`fit_for_topic` 字段是精华**。它不只描述案例，还给出「这个案例适合衍生出什么类型、什么难度的选题」——把案例与选题直接接上，避免调研与实际开题脱节。

## 扩展知识库

`assets/case_library.json` 是唯一数据源：

- **加案例**：往对应方向的 `cases` 数组追加，字段见 `references/case-card-spec.md`
- **加方向**：在 `directions` 下新建键，**务必补齐 `aliases`**（否则用户换个说法命不中）与 `keywords`
- **加建模模板**：`topic_patterns.json` 的 `modeling_plan_templates.by_direction` 下按方向名新建

新方向若没有对应的建模模板，脚本会自动回退到 `generic` 模板，不会报错。

## 故障排查

| 现象 | 原因与处理 |
| --- | --- |
| 方向显示「未在库内·需联网检索」 | 正常。走 `search-playbook.md` 联网检索后，把案例回写进 `case_library.json` |
| 报告里出现红色 `〔待补充〕` | 对应字段未提供。补齐 `direction_scope` / `direction_why` / `rationale` 四键即可 |
| 出现「缺少来源 URL」红标 | 案例 JSON 里缺 `url`。补上原始出处链接，无来源的案例应直接删除 |
| 案例数不足 3 个 | 脚本自动补空白卡片。若检索确实找不到 3 个，如实说明并补充国际对标或邻近方向类比（须标注为类比） |
| 别名命不中（如「水利工程」） | 新方向，需在 `case_library.json` 中新建并补 `aliases` |

## 诚实性红线（不可越过）

1. **不编造案例**。检索不到就如实说检索不到，不得用相似方向案例冒充。
2. **不放大数据**。原文写「降低 40%」就写 40%，不写成「大幅降低」也不写成「接近一半」。
3. **不把企业自研能力说成行业普适做法**。
4. **推断必须标注**。「预计可提升 X%」要写明这是推断而非实测。
5. **交付前自检**：过一遍 `search-playbook.md` 第七节与 `topic-evaluation.md` 第六节的清单。
