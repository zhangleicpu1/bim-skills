# 命名规范与测试方法（naming-and-testing）

---

## 第一部分 · 命名规范

命名规范的投入回报是族库管理里最高的——一个混乱的族库，三个月后连创建者自己都找不到构件。

### 1.1 标准依据

**GB/T 51269-2017《建筑信息模型分类和编码标准》**

| 项 | 内容 |
| --- | --- |
| 定位 | 中国 BIM 标准体系核心层，属基础数据标准，与 IFC、IDM 共同构成基础框架 |
| 发布 | 住房和城乡建设部，2017-10-25 发布，2018 年出版 |
| 发布单位 | 中国建筑工业出版社 |
| 适用范围 | 民用建筑及通用工业厂房建筑信息模型中信息的分类和编码 |
| 分类体系 | 依据 ISO 12006-2，与 OmniClass 关联，采用大类/中类/小类/细类 4 层级 |
| 编码结构 | 表代码-大类代码.中类代码.小类代码.细类代码，各级代码 2 位数字 |
| 示例 | 「土方机械」编码为 `32-04.05.00` |

**编码长度规则**：
- 大类：6 位（前 2 位为大类代码，后 4 位补 0）
- 中类：6 位（前 2 位大类 + 中类代码，后 2 位补 0）
- 小类：6 位（前 4 位为上位类代码 + 小类代码）
- 细类：8 位（小类编码后增 2 位）

**重要提示**：项目若要求编码，**必须通过共享参数承载**，族参数无法随 IFC 导出保留。
导出后应体现为用户定义属性集，才能实现设计到运维的语义连续。

### 1.2 族文件命名

**推荐格式**：

```
{专业代号}-{类别缩写}-{构件名称}-{关键规格}-{LOD}.rfa
```

**示例**：`ST-FRM-混凝土框架梁-300x700-LOD350.rfa`

**专业代号表**：

| 代号 | 专业 | 代号 | 专业 |
| --- | --- | --- | --- |
| AR | 建筑 | TL | 隧道 |
| ST | 结构 | GE | 岩土 |
| ME | 暖通 | NU | 核工业 |
| PL | 给排水 | | |
| EL | 电气 | | |

**类别缩写示例**：

| 缩写 | 类别 | 缩写 | 类别 |
| --- | --- | --- | --- |
| DOR | 门 | PIP | 管道 |
| WIN | 窗 | DCT | 风管 |
| COL | 结构柱 | CTR | 桥架 |
| FRM | 结构框架 | HNG | 支吊架 |
| SEC | 盾构管片 | FND | 基础 |
| ANC | 锚杆 | RAL | 栏杆 |
| SUP | 支护 | MON | 监测点 |
| CRT | 幕墙嵌板 | | |

**硬性规则**：
- 不用空格，用短横线连接
- 不用中文标点，不用特殊字符 `\ / : * ? " < > |`
- 规格写法统一：`300x700` 不要混用 `300×700`、`300*700`
- 同一项目族库内命名法统一，不要中英混用

### 1.3 参数命名

**推荐**：中文语义化命名，避免缩写与拼音。

| 好的命名 | 差的命名 | 问题 |
| --- | --- | --- |
| 洞口宽度 | DKWD | 拼音缩写，新人看不懂 |
| 铅当量 | PbEquiv | 中英混用 |
| 杆体总长 | L_total | 下划线+英文，与中文族库不统一 |
| 管片外径 | 外径 | 语境不明，跨族时歧义 |
| 环向螺栓数量 | BoltNum1 | 无法判断是什么螺栓 |

**规则**：
1. **同一概念在所有族中称谓必须一致**——「洞口宽度」不要在一个族叫「洞口宽」、另一个叫「门洞宽度」
2. 不要用 Revit 内置参数名做自定义参数名（尤其不要新建叫「宽度」的参数去覆盖内置参数——会导致族样板自带参数失效）
3. 涉及明细表统计的字段，命名要与项目参数表/企业标准对齐
4. **单位不写进参数名**（写「杆体总长」不写「杆体总长mm」），单位由数据类型决定

### 1.4 族类型命名

**格式**：`{构件简称}-{关键规格}`

**示例**：`KL-300x700`、`SG-φ6200`、`MG-φ25`、`QZ-800x800`

## 第二部分 · 测试方法

族编辑器里正确 **≠** 项目里正确。以下 10 项测试中，第 4、5、8 项只有放到项目环境才暴露问题。

### 2.1 参数弯曲测试

| 项 | 内容 |
| --- | --- |
| 怎么做 | 在「族类型」对话框逐个修改参数，每次只改一个，观察几何是否按预期变化 |
| 通过标准 | 每个参数都能正确驱动几何，无报错、无跳变、无非预期变形 |
| 为什么 | 最基础也最有效。**逐个改**而不是一次全改，出问题时才能定位到具体参数 |

### 2.2 极端值测试

| 项 | 内容 |
| --- | --- |
| 怎么做 | 把尺寸参数设到设计允许的最小值与最大值，甚至略微超出 |
| 通过标准 | 极端尺寸下几何不变形、不翻转、不消失 |
| 为什么 | 很多族在常规尺寸下正常，一拉到极端值就翻转破面。现场一定会遇到非常规尺寸 |

### 2.3 类型切换测试

| 项 | 内容 |
| --- | --- |
| 怎么做 | 在族类型中逐个切换所有类型，检查几何与材质是否正确跟随 |
| 通过标准 | 每个类型都正确，材质正确切换 |
| 为什么 | 多类型族最容易出现某几个类型漏赋值 |

### 2.4 项目环境测试

| 项 | 内容 |
| --- | --- |
| 怎么做 | 载入**空白**测试项目，放置若干实例，检查放置点、方向、宿主关系、旋转与镜像 |
| 通过标准 | 插入点位置合理；宿主行为正确；旋转/镜像正常；无警告 |
| 为什么 | 插入点位置与宿主关系只有在项目里才暴露问题 |

> 一定要用**空白项目**测试，不要拿正在做的项目试——有问题的族可能污染正式模型。

### 2.5 视图与详细程度测试

| 项 | 内容 |
| --- | --- |
| 怎么做 | 在平面、立面、剖面、三维视图中检查，并切换粗略/中等/精细三种详细程度 |
| 通过标准 | 各视图表达合理；粗略程度下有简化表达；无破面黑面；符号线在正确视图显示 |
| 为什么 | 出图依赖视图表达。很多族三维正常但平面一片空白——通常是符号线未指定可见性 |

### 2.6 出图比例测试

| 项 | 内容 |
| --- | --- |
| 怎么做 | 在常用比例（1:50、1:100、1:200）下检查线型与符号可读性 |
| 通过标准 | 常用比例下表达清晰，不糊、不过粗 |
| 为什么 | 族按真实尺寸建，但图纸按比例显示。小尺寸构件在大比例下可能糊成一个点 |

### 2.7 标记测试

| 项 | 内容 |
| --- | --- |
| 怎么做 | 给构件添加标记，检查标记能否正确读取参数值并显示 |
| 通过标准 | 标记显示正确的参数值，位置合理 |
| 为什么 | 标记读不到值，通常说明参数的数据类型或分组设置有问题 |

### 2.8 明细表测试

| 项 | 内容 |
| --- | --- |
| 怎么做 | 创建明细表，确认需要的参数能出现在可选字段中，且统计数量正确 |
| 通过标准 | 关键参数都能进明细表；数量、长度、体积统计正确 |
| 为什么 | 参数能否进明细表取决于**族类别**与参数类型。这件事必须在**建族前**验证，不是建完才发现 |

> 典型踩坑：用「公制常规模型」建的族无法统计长度/体积/宽度，只能统计个数。等发现时已经晚了。

### 2.9 文件清理与体积测试

| 项 | 内容 |
| --- | --- |
| 怎么做 | 执行「清除未使用项」，检查文件大小与打开速度 |
| 通过标准 | 无冗余项；文件体积合理；项目中使用不卡顿 |
| 为什么 | 族会被反复载入项目，体积过大会拖垮整个模型 |

### 2.10 协同一致测试

| 项 | 内容 |
| --- | --- |
| 怎么做 | 与其他专业模型合并，做碰撞检查 |
| 通过标准 | 占位空间准确，碰撞结果符合预期 |
| 为什么 | 族的占位空间是否真实，只有多专业合并时才看得出来 |

## 第三部分 · 发布检查流程

```
① 参数设计自查（parameter-design.md 第七节）
        ↓
② 族编辑器内测试（2.1 ─ 2.3）
        ↓
③ 空白项目环境测试（2.4 ─ 2.8）
        ↓
④ 体积与协同测试（2.9 ─ 2.10）
        ↓
⑤ 执行「清除未使用项」
        ↓
⑥ 确认命名符合规范
        ↓
⑦ 记录族参数说明，入库
```

**未通过全部检查不得发布。** 一个有问题的族进入项目，后续所有使用它的模型都会被污染——修复成本远高于重建。

## 第四部分 · 团队协作建议

- **样板文件先行**：开工前统一项目样板、族样板、共享参数文件、命名规范，指定专人维护
- **族库分层**：按 LOD 分区（LOD200 方案阶段 / LOD300 施工图 / LOD400 加工），避免早期模型被精细族拖垮
- **定期审计**：每季度检查一次族库——未被任何项目使用的族归入归档；重复几何的族合并；从未被填写的参数删除
- **参数标准化**：同概念参数名全库统一，是降低新人学习成本最有效的手段
